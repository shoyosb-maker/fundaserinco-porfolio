04Seguridad y datos de clientes

La autorización no se decide en el frontend ni en una condición de JavaScript: se decide en la base de datos. Cada tabla con datos de usuario lleva Row Level Security activo, así que una consulta solo devuelve las filas que ese usuario puede ver, aunque el código pida la tabla completa.

Cómo se ve una política PostgreSQL · cada sede solo ve sus propias filas

-- 1. activar el aislamiento por fila en la tabla
alter table public.solicitudes enable row level security;

-- 2. leer: solo las filas de la sede de la sesión
create policy solicitudes_lectura on public.solicitudes
  for select to app_usuario
  using ( sede_id = current_setting('app.sede_id')::uuid );

-- 3. escribir: no se puede crear una fila de otra sede
create policy solicitudes_alta on public.solicitudes
  for insert to app_usuario
  with check ( sede_id = current_setting('app.sede_id')::uuid );

-- 4. que ni el propietario de la tabla se salte las políticas
alter table public.solicitudes force row level security;

En Supabase la política se escribe igual, con auth.uid() en lugar de la variable de sesión: using (user_id = auth.uid()). Lo que no cambia es el principio: el filtro vive en la base y se aplica a cualquier cliente que se conecte, incluido un script suelto con la cadena de conexión en la mano.

Datos personales. El tratamiento se documenta según la Ley 1581 de 2012 y el Decreto 1377 de 2013: finalidad, base de datos registrada ante la SIC, aviso de privacidad, canal de consulta y reclamo, y procedimiento de borrado. Con proveedores de nube se firma el acuerdo de tratamiento antes de mover información real.

10Preguntas frecuentes

¿De quién es el código?

Del cliente. Se entrega en un repositorio git con su historial completo, sin dependencias cerradas con el proveedor. Si se quiere, se transfiere también el dominio, el hosting y las cuentas asociadas.

¿Qué pasa después de la entrega?

Hay garantía por defectos y un SLA contratado. El mantenimiento mensual es opcional e incluye monitoreo, respaldos, actualizaciones de seguridad y una bolsa de horas.

¿Cómo evitan que la IA invente datos?

El asistente responde sobre el catálogo y los documentos cargados, no sobre su imaginación: se limita el contexto, se le prohíbe prometer plazos o precios fuera de rango y se registra cada conversación para auditoría. Cuando no sabe, deriva a una persona.

¿Qué es RLS y qué impide exactamente?

Row Level Security es una función de PostgreSQL que filtra las filas según quién consulta. Una misma sentencia select * from solicitudes devuelve un conjunto distinto para el gerente de una sede y para el de otra, sin que el código de la aplicación tenga que acordarse de añadir el filtro. Impide la fuga lateral: que un usuario manipule un identificador en la URL o en una petición a la API y termine leyendo datos de otra sede. Se complementa con force row level security, que impide que incluso el dueño de la tabla se salte las políticas por descuido.

¿Trabajan sobre un sistema existente?

Sí. Se hace auditoría técnica, se define qué se conserva y se avanza por partes sin detener la operación. Reescribir todo de una sola vez es la forma más costosa de fracasar.
